## 0. 结论摘要

**总体判定：方案方向成立，但当前版本不可直接作为开发基准。**

文档本身质量较高——分层架构、职责划分、去抖策略、法规约束、风险表、测试用例都具备，明显高于一般设计文档的水准。问题不在"写得好不好"，而在**地基假设与真实硬件不符**：

> 文档假设的接收端是"带轮询调度与断连缓存的完整网关"，假设节点能上报 PEAK/AVG/NOISE/PULSE_CNT/报警等级/UTC 时间戳；
> 真实硬件是"接收端 MCU 仅做收发"，节点只上报"强度 + 电池 + 序号"。

这个落差会**连锁击穿第 2.3、3.3、4.2、4.3、4.5、5.2 章以及附录 A.1、附录 B(TC-05)** ——即文档中"网关侧"和"节点上报侧"的全部承载体，都需要重写。

**一个反直觉的好消息：真实硬件比文档假设的更简单，改完方案也会更简单。**

| 维度 | 判定 | 一句话理由 |
|---|---|---|
| 产品定位与场景匹配 | ✅ 成立 | 已确认"固定安装长期在线 + 值班室常驻有人值守 + 仅本地"，与文档"分布式声学监测网络"定位一致（说明书的便携形态属旧款） |
| 通信链路可行性 | ⚠️ 基本成立，职责需重划 | 链路通，但轮询时序、缓存补传、RSSI 补填、校时共 4 项职责在真实硬件上无承接方 |
| 协议设计合理性 | ⚠️ 框架合理，字段必须重定 | 帧结构/CRC/命令集骨架是对的，但上行帧有一半字段填不出来，且存在 2 处内部自相矛盾 |
| 技术选型合理性 | ⚠️ 开发期合理，交付期论证不足 | 7.2 章只论证了"AI 开发效率"，没论证"值守场景运维成本"，缺交付形态这一维度 |
| 范围与计划可行性 | ⚠️ 范围偏大，计划偏乐观 | 按 50 节点做的容量/表结构属过度设计；S4 一个阶段塞了 4 件独立的事；缺"协议冻结"和"现场标定"两个阶段 |
| 改动成本 | ✅ 低 | 四层（节点固件 / 接收端固件 / 协议 / 上位机）均可改，且精简后帧更短、带宽更省、节点固件更简单 |

**进入开发前必须先完成的一件事：协议与字段基线重置（第 7 章给出修订稿）。** 完成后再进 S1，文档原有的 S1–S5 骨架可以沿用。

## 3. A 级问题（阻断，必须先解决）

### A1. 第 2.3 章「职责划分」与接收端真实能力不符

文档把 4 项职责判给接收端网关：

| 文档判给网关的职责 | 真实硬件能否承接 | 后果 |
|---|---|---|
| LoRa 空口收发、CAD 退避 | ✅ 能（透传/转发） | 无 |
| **轮询调度（一问一答）** | ⚠️ 部分——须由 PC 编时序后下发给接收端转发 | PC 侧需新增轮询调度器；且**须确认接收端是否支持 PC 控制收发切换**，否则一问一答时序不可控 |
| **原始帧缓存（断连期间）** | ❌ 不能 | 上位机断连期间数据**必然丢失**；文档 R4 对策、附录 B 的 **TC-05 测试用例（断连 10 分钟后自动补传）无法实现**，必须从验收标准中删除或改为"上位机侧重连对齐 SEQ 断点" |
| **节点时钟校准（接受校时）** | ❌ 不能 | 见 A3，校时命令与 R5 风险描述均需重写 |
| **RSSI / SNR 补填** | ❌ 不能 | 文档 M1「链路质量：实时显示 RSSI 与 SNR，并提供历史曲线」**无数据来源**；M2 表格 RSSI/SNR 两列恒为 `--` |

**处置建议**：重写 2.3 章为三栏（节点侧 / 接收端侧 / 上位机侧），把轮询调度、时间戳、缓存策略、链路质量全部收敛到上位机侧；同时明确"接收端固件需新增的能力清单"（要么接受端加能力，要么上位机降期望）。

### A2. 第 3.3 章上行帧字段大面积无数据来源

文档定义 25 字节上行帧，与真实节点能力逐一对照：

| 偏移 | 字段 | 真实数据源 | 判定 |
|---|---|---|---|
| 0–1 / 2 / 3 / 4–5 / 6–7 | SYNC / VER / MSG_TYPE / DEV_ID / SEQ | 有（序号已确认） | ✅ 保留 |
| 8–11 | TIMESTAMP（UTC 4B） | **节点无时间戳** | ❌ 删除，改由上位机打接收时刻 |
| 12 | FLAG bit0 报警锁存 | 节点有蜂鸣器/绿灯，可上报 | ⚠️ 需确认，可保留 |
| 12 | FLAG bit1-2 报警等级 | **节点不报等级** | ❌ 删除，改由上位机按阈值判级（这是更合理的设计） |
| 12 | FLAG bit3 传感器故障 / bit4 低电 | 低电可从电池电压推 | ⚠️ 可保留 |
| 13–14 | PEAK | 节点只有一个强度值 | ❌ 删除或与 AVG 合并为单一 STRENGTH |
| 15–16 | AVG | 同上 | ❌ 同上 |
| 17–18 | NOISE 噪声基线 | 无 | ❌ 删除 |
| 19–20 | PULSE_CNT 脉冲计数 | 无 | ❌ 删除（连带 4.4 章"双 Y 轴：右轴脉冲计数"失据） |
| 21 | BATTERY | 有 | ✅ 保留 |
| 22 | RSVD | — | ✅ 保留 |
| 23–24 | CRC16 | — | ✅ 保留 |
| 帧尾附加 | RSSI / SNR | 接收端不补填 | ❌ 删除或降为可选 |

**结论：25 字节中约 40% 的字段当前填不出来。** 精简后帧长可压到 13–14 字节，LoRa SF7/BW125 下空中时间从约 62 ms 降到约 50 ms（估算），**更省带宽、更低误码率、更远离"单次发射 < 1 s"红线**。这是本次评估中最正向的一项修改。

### A3. 数据模型（5.2）与主界面表格（4.3）字段无来源

`t_sample` 表 10 个业务字段中，`peak / avg / noise / pulse_cnt / rssi / snr` 共 6 个无数据源。连锁后果：

- **4.3 章 M2 表格 10 列中有 5 列将恒为 `--`**（峰值、噪声基线、脉冲计数、RSSI、SNR），与 6.1 章"容错显示：数值无效时显示 `--`，禁止出现 NaN / null / 0 占位"的规范自相冲突——规范本身是对的，但表格不该按不存在的字段来排。
- `t_alarm.level` 依赖节点上报等级，实际须由上位机计算后写入。这一点文档未明确定论（见 A5）。

**处置建议**：`t_sample` 精简为 `id / dev_id / ts / strength / battery / flag`，把上位机判定结果（`alarm_level`、去抖状态）作为派生列；`t_linkstat`（RSSI/SNR）本期不建表，待接收端具备上报能力后再加。

### A4. 文档内部自相矛盾：0x11 写配置载荷长度

| 位置 | 描述 |
|---|---|
| 3.5 章命令集 | 载荷内容 = "阈值×3 + 周期 + 增益 + SF"，即 3×2 + 2 + 1 + 1 = **10 字节** |
| 附录 A.2 示例 | LEN = **0x06**，载荷只含 3 个阈值（6 字节），无周期、增益、SF |

两处不一致，双方按不同理解并行开发必然返工（这正是文档 R1 描述的风险，却在自己文档里出现了）。

**处置建议**：二选一并统一。建议**拆成两条命令**更清晰：`0x11 写阈值`（3×2=6B）与 `0x16 写运行参数`（周期 2B + 增益 1B + SF 1B = 4B），各自独立下发、独立校验。

### A5. 报警等级"由谁判定"未定论

文档同时存在两种互斥设计：

- 3.3 章 FLAG 的 bit1-2 表示"报警等级"，暗示**节点判定**；
- 4.5 章要求四级分级（正常/关注/预警/报警）且"阈值支持按节点单独设置，且可远程下发"，暗示**上位机判定**。

真实硬件节点不报等级，**结论只能是上位机判定**。这个定论必须写进文档——它决定了 4.5 章去抖引擎的实现位置（应在业务层，符合 7.5 章"分层不可越"），也决定了 FLAG 字段可以退化。

### A6. 法规类别前提缺失（影响能否上市）

470–510 MHz 在现行《微功率短距离无线电发射设备目录和技术要求》中，归属 **"（四）民用计量仪表"** 类别。文档 3.1.2 章引用的全部技术参数（50 mW e.r.p、占用带宽 ≤ 500 kHz、单次发射持续 ≤ 1 s、须具备发射前搜寻且不可被用户关闭、限建筑楼宇/小区/村庄小范围组网）**与该类别条款逐条对得上**，说明文档作者读过原文。

但文档**漏掉了最关键的一句前提**：该频段微功率豁免的前提是**设备类别为民用计量仪表**。QYH-GD300 是局部放电故障定位仪，**不属于民用计量仪表**。

**风险后果**：这不是"限定频率即可合规"，而是"**可能整个频段不可用，或必须走型号核准（SRRC）路径**"——比文档 R9 描述的风险严重。另需注意同类别条款中的"**任意时刻限单个信道发射**"，会约束多信道/跳频策略。

**处置建议**：R9 对策由"严格限定频率与功率"升级为"**先行确认频段合规路径（微功率豁免 or 型号核准），必要时评估替代频段**"，并把这一项从"上市前风险"提前到"方案冻结前必须澄清"。

### A7. 命令 0x20「历史补传」指向矛盾

3.5 章 `0x20 历史补传：起始 SEQ + 结束 SEQ` 要求**节点侧**回放历史缓存；2.3 章又把"原始帧缓存（断连期间）"判给**网关侧**。两个缓存主体互相推诿，且节点侧缓存需要 Flash 磨损管理方案（文档完全未涉及）。

**处置建议**：明确二选一。以"接收端仅做收发"为前提，本期现实选择是——**不做补传**，改为上位机侧记录 SEQ 断点并显式标注数据缺口（曲线显示断点，不伪造连续）。若客户强需求补传，则须在接收端或节点增加 Flash 缓存能力，属独立工作量，应单独立项。

## 4. B 级问题（重要，建议阶段前修正）

### B1. 强度量纲错误：dB 定标不成立

已确认强度为"**相对值，无绝对基准**"，但文档全篇按 `dB` 处理：

- 3.3 章 `PEAK / AVG / NOISE` 定标 0.1 dB；
- 4.3 章表格列名"实时强度（dB）/ 峰值（dB）/ 噪声基线（dB）"；
- 4.5 章阈值按 dB 设定（附录 A.2 示例：关注 30.0 dB / 预警 50.0 dB / 报警 60.0 dB）。

**问题**：dB 是相对量，没有参考基准时"58.7 dB"这个数值无物理意义，无法与其他仪器比对、无法跨项目复用阈值、也无法做验收标定。

**处置建议**：全篇改用中性的"强度单位（原始刻度值）"，字段用 `uint16`（或按节点实际位宽取 `uint8`）。阈值同样以原始刻度设定，并在文档中补一节"**阈值标定方法**"（现场实测本底噪声 → 取本底的若干倍/若干倍标准差作为关注阈值 → 依次上推预警、报警），这比拍一个 dB 数字可靠得多。

### B2. M5「强度对比定位」的成立前提未定义

文档 4.6 章的算法说明是对的："同类传感器、**同等增益条件下**，接收强度最高的测点距放电源最近"。但这一前提在真实系统中很难自然满足：

- 各节点的传感器灵敏度存在个体差异；
- **固定安装的耦合方式是最大变量**——磁吸、胶粘、耦合剂、压紧力矩、壳体漆层厚度都会显著改变声波传到效率；
- 节点增益可独立配置（3.5 章 0x11 命令含"增益"），一旦现场为不同节点设了不同增益，跨节点强度就不可比。

**连锁后果**：强度不可比 → "最强路推定"会指错 → 而产品名恰好叫"**故障定位仪**"，客户预期是"定位"，实际只能给"**区域提示**"。这个预期落差会在验收时集中爆发。

**处置建议**：
1. 文档中明确标注该功能为"**疑似放电源区域提示，非精确定位**"，并写入产品说明与验收标准；
2. 补充"**部署期一致性标定流程**"：同一信号源对全部节点做一遍响应核对，记录各节点修正系数，上位机按系数归一化后再排名；
3. 增加"节点增益变更留痕"——任何节点增益改动都要写入操作日志，否则历史曲线的可比性被静默破坏。

### B3. 时间基准与校时链路不成立

- 节点无时间戳（已确认），故 3.5 章 `0x12 校时` 广播 UTC 无接收意义，除非节点具备 RTC（**待确认**）。
- 文档 R5"时钟错乱导致曲线乱序"的成因描述与实际不符：真实风险不是节点时钟错乱，而是**上位机用接收时刻打戳，串口/LoRa 延迟会直接进入时间轴**。好消息是单室 5–20 台、周期级上报，延迟量级远小于上报周期，可接受。
- 由此新增一项文档未覆盖的依赖：**PC 侧必须有可靠时间源**（NTP / 手动校时），因为长期趋势（"长期劣化预警"）的横轴完全由 PC 时钟决定。PC 时钟漂移几个月，趋势结论就错了。

**处置建议**：删掉 0x12 校时（或降为"读节点运行秒"）；新增 8.x 节"时钟要求：上位机须启用 NTP，并在界面上暴露当前时钟偏差状态"；R5 改写为"上位机时钟源失效导致趋势横轴漂移"。

### B4. 技术选型：只论证了开发期，没论证交付期

文档 7.1/7.2 的主选是 Vue 3 + FastAPI 双进程 + 浏览器访问 localhost。7.2 章给出的三条理由（声明式 UI 利于 AI 生成、可截屏验证闭环、一套前端兼顾本地与远程）**在开发期全部成立**，评估认可。

但本项目的真实交付场景是"**值班室常驻 + 有人值守 + 仅本地 + 无硬时间约束**"，这个场景的验收标准不是开发效率，而是**运维可靠性**。文档未覆盖以下缺口：

| 缺口 | 具体表现 | 严重度 |
|---|---|---|
| 开机自启与崩溃恢复 | 双进程（Python 服务 + 浏览器）需两个自启项与看门狗；浏览器被误关后数据仍在但人看不见 | 高 |
| **浏览器自动播放策略** | Chrome/Edge 要求用户手势后才允许播放音频——**无人值守时段报警可能完全没有声音**，直接击穿 4.5 章的声光报警 | **高** |
| 单 exe 分发 | PyInstaller 单文件 + 内嵌前端 dist，体积大且易被杀软误报；现场 IT 可能禁止安装 | 中 |
| localhost 安全 | 服务仅监听 127.0.0.1 是对的，但浏览器内任意页面均可访问 `localhost:8000`，WebSocket 无鉴权存在跨站连接风险 | 中 |
| 7×24 内存 | 8.1 章要求"连续运行 24 h 增量 < 100 MB"，浏览器进程是这一指标的主要风险源 | 中 |
| 缩放兼容 | 8.3 章要求支持 150%/200% 缩放，浏览器缩放与 Windows DPI 缩放叠加后表现需实测 | 低 |

**处置建议（保留主选，补齐交付形态）**：

- **推荐**：内核仍用 Vue 3 + FastAPI，但交付形态改为**桌面壳单 exe**（pywebview，或 Electron/WebView2 壳）。FastAPI 托管前端静态资源、仅绑 127.0.0.1 并加本地 token；壳进程负责开机自启、崩溃自重启、窗口全屏常驻。这样既保留"AI 生成友好 + 可截屏验证"的开发优势，又消掉"手动开浏览器"的运维坑，同时解决音频自动播放限制（原生壳内可正常播放）。
- **备选 C# WPF + ScottPlot**：若团队更看重"零运行时依赖 + 现场 IT 友好 + 单 exe"，这条路更省事，代价是 AI 迭代效率下降、失去截屏验证回路。文档 7.1 把它列为"备选整体方案"是合理的，但 7.2 章应把"交付形态与运维成本"补进选型依据，否则这个结论的论证是不完整的。
- **第三备选 PySide6 不建议采用**，理由与文档一致：命令式布局代码冗长（addWidget / setLayout 序列），AI 生成时漏调用风险高。

### B5. 数据生命周期：SQLite 不支持"按月分区"

5.3 章"容量管理：`t_sample` 建议**按月分区**，并开启降采样归档"——**SQLite 没有原生分区表**。这句表述会误导实现者。

另：容量按 50 节点估算（2600 万条/年），实际 5–20 台，即约 **105 万–1050 万条/年**（按 60 s 周期），SQLite 配合 `(dev_id, ts)` 索引完全可承载，属于过度设计（无害，但会误导后续维护者以为需要上时序库）。

**处置建议**：改为"按月**分表**（`t_sample_YYYYMM`）或单表 + 定期归档/降采样"；容量核算按实际 20 台重算；补充"**磁盘空间监控与自动清理策略**"（文档对 `t_raw_frame` 有滚动清理，但对 `t_sample` 只有保留策略，没有空间告警）。

### B7. 报警阈值三级缺少标定方法

4.5.1 章定义了正常/关注/预警/报警四级，但**没说三级阈值从哪来**。附录 A.2 示例里的 30/50/60 dB 无出处。现场若拍脑袋定阈值，就会直接产生 R2 风险（误报刷屏）。

**处置建议**：新增"阈值标定与自学习"一节：现场静置采集本底 → 统计均值与标准差 → 关注阈值 = 本底 + k₁σ、预警 = 本底 + k₂σ、报警 = 本底 + k₃σ；并支持"按节点独立标定"，与 4.5.3 章"阈值支持按节点单独设置"呼应。

### B8. 现场射频风险被低估

文档 R7 把空口风险聚焦在"SF 参数拍脑袋定错"。但在**开关柜/配电室**环境中，470 MHz 的真实风险是**金属柜体的屏蔽与多径反射**，而非 SF 档位。好消息是本项目为**单室 5–20 台**，距离近，链路预算充裕，SF7 大概率够用。

**处置建议**：在 S5 前置条件中增加"**RF 勘测**"（不只是天线位置调优）：逐节点实测 RSSI/丢包率，确认金属柜体遮挡下的链路余量，再决定 SF 档位。

## 7. 修订建议稿

### 7.1 上行帧（节点 → 接收端 → 上位机）建议版

按真实节点能力精简，14 字节封顶（强度若为 8 位则 13 字节）：

| 偏移 | 字段 | 长度 | 类型 | 说明 |
|---|---|---|---|---|
| 0–1 | SYNC | 2 | uint16 | 固定 `0xAA55` |
| 2 | VER | 1 | uint8 | 协议版本，当前 `0x01` |
| 3 | MSG_TYPE | 1 | uint8 | `0x01` 周期 / `0x02` 报警 / `0x03` 心跳 / `0x04` 应答 |
| 4–5 | DEV_ID | 2 | uint16 | 节点地址，`0x0000` 保留广播 |
| 6–7 | SEQ | 2 | uint16 | 帧序号，循环递增，用于丢包与断点检测 |
| 8–9 | STRENGTH | 2 | uint16 | 强度原始刻度值（**非 dB**），位宽按节点实际能力确定 |
| 10 | BATTERY | 1 | uint8 | 电池电压 ×10（如 `0x7A` = 12.2 V） |
| 11 | FLAG | 1 | uint8 | bit0 本地报警锁存 / bit1 传感器故障 / bit2 低电 / bit3-7 保留 |
| 12–13 | CRC16 | 2 | uint16 | CRC-16/MODBUS，覆盖偏移 0–11 |

**变化说明**：删除 TIMESTAMP、PEAK、AVG、NOISE、PULSE_CNT、报警等级位、RSSI/SNR 附加字段（共约 11 字节）。MSG_TYPE 删去 `0x05 补传`（A7）。时间戳由上位机在收到帧时打。报警等级由上位机业务层判定。SF7/BW125 下空中时间约 50 ms（估算），较原 25 字节方案显著缩短。

### 7.2 下行帧建议版

下行帧骨架（3.4 章）无需改动，仅修正命令载荷定义：

| 命令字 | 名称 | 载荷 | 修正点 |
|---|---|---|---|
| `0x10` | 读配置 | 空 | 保留 |
| `0x11` | **写阈值** | 关注 2B + 预警 2B + 报警 2B（6B） | 从原 `0x11` 拆出，与附录 A.2 现有示例对齐（A4） |
| `0x16` | **写运行参数**（新增） | 上报周期 2B + 增益 1B + SF 1B（4B） | 从原 `0x11` 拆出的另一半 |
| `0x12` | 校时 | — | **删除**（节点无时间戳/RTC，见 B3）；若节点有 RTC，改为"读节点运行秒"用于漂移观测 |
| `0x13` | 报警静音 | 使能位 1B | 保留 |
| `0x14` | 报警复位 | 空 | 保留（与说明书"报警灯与恢复按钮一体"呼应） |
| `0x15` | 节点重启 | 空 | 保留 |
| `0x20` | 历史补传 | — | **本期删除**（A7）；如需保留，须先为接收端或节点补 Flash 缓存能力并单独立项 |
| `0x21` | 轮询单次 | 空 | 保留。**建议提升为默认机制**：由 PC 侧轮询调度器逐节点下发 |

| 8 | 节点是否有本地报警锁存与声光，能否上报该标志？ | 决定 FLAG bit0 的有效性（A2） |
| 9 | 现场传感器安装与耦合方式？是否做一致性标定？ | 决定 M5 定位可信度（B2） |
| 10 | 三级报警阈值的初始值来源（经验值 / 现场标定 / 自学习）？ | 决定 4.5 章与 B7 的实现方式 |
| 11 | 现场是否有可用网络（NTP），或有其他授时手段？ | 决定长期趋势横轴可靠性（B3） |
| 12 | 470–510 MHz 频段的合规路径是否已确认（微功率豁免 or 型号核准）？ | 决定产品能否上市（A6） |

---

## 9. 最终结论

1. **方案方向正确，不需要推翻。** 分层架构（2.2）、职责划分的思路（2.3，虽内容需改）、报警去抖（4.5.2）、法规意识（3.1.2）、风险表（第 10 章）、测试用例（附录 B）都是好设计，7.5 章"分层不可越"三条硬约束尤其值得保留。

2. **当前版本不能直接开工，必须先做一次"协议与字段基线重置"。** 7 项 A 级问题中的 A1/A2/A3/A4/A5/A7 都源自同一个根因——文档在不知道真实硬件能力的前提下补齐了协议字段。这个根因不解决，S1 一开始就会返工。

3. **重置的代价很低，收益很明确。** 四层都可改；精简后的上行帧从 25 字节降到 13–14 字节，空口时间更短、误码率更低、远离法规红线，节点固件也更简单。这是个少见的"减法同时改善合规性与可靠性"的修改。

4. **两个必须在方案冻结前澄清的外部前提**：470–510 MHz 的合规路径（A6，关系到能否上市），以及接收端固件是否愿意为轮询时序与链路质量补能力（A1，关系到功能范围）。

5. **一项预期管理**：产品名"故障定位仪"，但软件侧只能实现"疑似区域提示"。这个落差必须在产品说明与验收标准中提前写清，否则会在验收环节集中爆发（B2）。

6. **一次交付形态的补课**：7.2 章的选型论证只覆盖了开发效率，需补"交付形态与运维成本"。建议保留 Vue 3 + FastAPI 内核，改用桌面壳单 exe 交付，可一并解决开机自启、崩溃恢复与报警音自动播放三件事（B4）。
